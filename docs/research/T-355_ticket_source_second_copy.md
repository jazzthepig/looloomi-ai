## 3. 唯一那 1 张不一致:LOOM 2024-11-25

* 我的票:出场日 **2024-12-29**,出场价 0.08112,理由 `sma20`,r = +0.3828495275982098。
* t197 的票:出场日 **2025-03-25**,出场价 **0.08112(同价)**,r = **+0.3828495275982098(同值)**。

机制(查了原始 bar):LOOM 的收盘价从 **2024-12-18 起冻结在 0.081120**(o/h/l/c 全同),一直冻到面板末日。
20 根收盘的均值在 2024-12-28 恰好等于 0.081120 —— `c < sma20` 是个**浮点平局**:
我这边的 numpy `sliding_window_view.mean` 求和顺序让均值落成 `0.08112000000000002`(> c),旗标成立 → 次日开盘出场;
t197 那边的求和顺序落成**恰好等于** c,平局判否 → 票留到 `bars_held` 满 120(2025-03-25,进场后第 120 根 bar)按到期出场。
**两条路径出场价完全相同 → r 相同 → 账户结果一字不差**(上表两栏逐位相同;这张票在引擎里被
notional_cap 挡掉,根本没进场)。

> 不是两份实现的规则分歧,是**冻结价上的浮点平局**。生产内核(Postgres `avg()`)倒向哪边取决于
> 浮点求和顺序 —— 不可控。这类「假出场」(信号/止损在死价上触发)用陈旧价格结账,不是真实成交价。

## 4. 口径坑(记下来,别再踩)

引擎的不变量③是「已实现盈亏 = Σ(r × 进场时每票风险额)」,风险额 = 名义 × sd,
所以喂进去的 **r 必须是 R 倍数**(生产 SQL 的 `r_mult`),不是简单收益。
第一版我把 r 写成 `r_mult × sd`(简单收益),引擎直接拦下:`不变量③不成立:diff=0.8368…`。
SQL 的口径 `r = (exit−entry)/(entry−stop) − 0.004·entry/(entry−stop)` 等价于 `r = [(exit/entry−1) − 0.004]/sd`。
`still` 票(窗口末还在场)没有出场价,r 记 0,只占名额、永不结算 —— 这条原来就对。

## 5. 生产侧:数据洞与闸门(需要 @seth 看)

生产 SQL 有个**数据完整度闸门**:`v_n_bars < greatest(20, 0.8*v_prev_bars)` 就停止扫描。
在我的宇宙(面板)上它**第 588 天就停**:`only 89 bars on 2022-02-26 (previous day 137)`。
查原始数据,原因不在交易规则,而是**面板本身有两个数据洞**:

| 日期 | 面板里的 bar 数 | 生产 `perp_bv_daily` 的行数 |
|---|---|---|
| 2022-02-25 | 137 | 124 |
| 2022-02-26 ~ 02-28 | **89** | **80** |
| 2022-03-01 | 137 | 124 |
| 2022-03-31 | 140 | 126 |
| 2022-04-01 | **92** | **80** |

整段 2465 天里只有这 2 天跌幅超过 20%(其余日期 bar 数平滑)。**生产表 `perp_bv_daily` 有同样的洞**
—— 即:**谁要是从 2020-07-18 重跑 `r_tickets_scan`,扫描会在 2022-02-26 之前停**,历史票本只剩 588 天
(开闸跑出来的版本:78 张票,closed 72 / blocked 6 —— 存 `t355_tickets_guard.json`)。
现在生产扫描没停,是因为 `r_tickets_state.last_d = 2026-11-10`(2026-11-11 09:12 UTC 跑过),
状态已经越过那两个洞 —— 状态是从后面起算的,不是从头扫的。

**主交付用的是「关掉数据完整度闸门」的版本**(闸门是运维闸、不是策略规则;卡里点名的规则是
信号/进场/止损/出场/到期)。开闸版本一并留档(`t355_tickets_guard.json`:scan_log + 78 张票,
其中 closed 72 / blocked 6;该文件的 `engine_tickets[].r` 字段是 §4 的 r 口径修正**之前**的产物,
它在这里只作闸门证据用,票面的 `r_mult` 是对的)。
